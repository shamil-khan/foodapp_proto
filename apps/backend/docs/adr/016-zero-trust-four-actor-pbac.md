# ADR-016: Zero-Trust Four-Actor PBAC & Elimination of `ALL_PERMISSIONS` / `SYSTEM` Bypasses

- **Status:** Implemented & Verified

## 1. Problem Statement & Architectural Goal

- **Business & Technical Problem:**
  1. **Wildcard Permission Leakage (`ALL_PERMISSIONS`):** `ALL_PERMISSIONS` combined tenant, customer, and platform rights into a single superset array used by token verification (`PosTokenService`), role caches (`RolePermissionCache`), and integration test scopes.
  2. **Unrestricted `SYSTEM` Actor Bypass (`actorSource === 'SYSTEM'`):** Every specification in `AuthorizationPolicy` (`HasPermissionSpec`, `SameRestaurantSpec`, `SameBranchSpec`, `SameUserSpec`, `CanDelegatePermissionsSpec`) and every scope resolver in `ScopedRepository` (`resolveBranchScope`, `resolveRestaurantScope`, `resolveUserScope`) short-circuited with `if (request.actorSource === 'SYSTEM') return true;` / `unrestricted: true`. Furthermore, unauthenticated HTTP requests initialized `RequestContext` with `actorSource: 'SYSTEM'` and `permissions: []` in `initDiScope`.
  3. **Ambiguous `GLOBAL_USER` Boundary:** Sharing `actorSource: 'GLOBAL_USER'` between storefront consumers (`CUSTOMER`) and platform specialists (`PLATFORM_ADMIN`) obscured the strict business invariant that business logins (`POS_STAFF` and `PLATFORM_STAFF`) must never act as personal food-ordering customers.
- **Architectural Goal:** Eliminate `ALL_PERMISSIONS` and `actorSource: 'SYSTEM'` completely across `@foodapp/db` and `@foodapp/backend`, enforce a strict zero-trust four-actor model (`'ANONYMOUS' | 'CUSTOMER' | 'POS_STAFF' | 'PLATFORM_STAFF'`) with zero permission or scope bypasses, and execute domain event consumers inside isolated per-event scopes derived from the originating event context.

## 2. Architectural Decisions (Q&A)

### Q1. `SYSTEM` Actor Scoping & Cross-Tenant Permissions

- **Considered Options (up to 5: Option A – Option E):**
  - _Option A:_ **Strict Scope OR Explicit Cross-Tenant Worker Rights (`system:*`)** — Define internal `system:*` permissions (e.g., `system:billing:settle`, `system:loyalty:settle`, `system:catalog:sync`) allowing background handlers or batch jobs to cross tenant/user boundaries without per-event scopes. — **Pros:** Single shared `bootScope` can handle multi-brand events without opening per-event scopes. | **Cons:** Introduces unused cross-tenant privileges when zero cron jobs or cross-restaurant operations exist in the greenfield codebase, widening the blast radius of any query bug.
  - _Option B (Selected):_ **Zero Bypass & Strict Single-Tenant / Single-User Scope (No `system:*` Rights)** — Remove all `actorSource === 'SYSTEM'` bypasses and add zero special `system:*` permissions; every execution must hold standard domain permissions and operate strictly within a single `restaurantId`, `branchId`, or `actorId` (with dedicated cron permissions or `platform:branches:read` for the upcoming Platform Admin Dashboard added strictly when those features are built). — **Pros:** Minimal blast radius, zero dead permissions (YAGNI), and 100% tenant isolation enforced by `ScopedRepository`. | **Cons:** Event subscribers that touch `ScopedRepository` (`BillingSettlementEventHandler`, `LoyaltySettlementEventHandler`) must open a lightweight per-event scope.
- **User Commentary & Trade-Off Evaluation:** Engineering Lead confirmed that this is a greenfield project with zero cron jobs and zero cross-restaurant operations today; when cron jobs or the Platform Admin Dashboard (e.g., monitoring branch operational status across brands) are introduced later, dedicated rights (such as `platform:branches:read` on `PLATFORM_ADMIN_PERMISSIONS`) will be added strictly as needed. Codebase inspection verified zero cross-restaurant runtime mutations exist today.
- **Selected Implementation:** Remove all `SYSTEM` bypasses and introduce no `system:*` wildcard/cross-tenant rights; enforce standard domain permissions and single-tenant/single-user scope on every execution.

### Q2. Four-Actor Zero-Trust Taxonomy (`ANONYMOUS`, `CUSTOMER`, `POS_STAFF`, `PLATFORM_STAFF`)

- **Considered Options (up to 5: Option A – Option E):**
  - _Option A (Selected):_ **Pure 4-Actor Zero-Trust Taxonomy (`'ANONYMOUS' | 'CUSTOMER' | 'POS_STAFF' | 'PLATFORM_STAFF'`)** — Eliminate `'SYSTEM'` completely, default unauthenticated HTTP requests to `'ANONYMOUS'`, and split `'GLOBAL_USER'` into `'CUSTOMER'` (Mobile + OTP login via Better Auth `phoneNumber` plugin -> `CUSTOMER_PERMISSIONS`) and `'PLATFORM_STAFF'` (corporate email + password -> `PLATFORM_ADMIN_PERMISSIONS` + brand-approved JIT `supportGrant`), alongside `'POS_STAFF'` (brand email + password -> `TENANT_PERMISSIONS` subset bound to `restaurantId` & `branchId`). — **Pros:** 1-to-1 mapping between authentication channel and `ActorSource`; enforces in the type system and domain policies that business logins (`POS_STAFF` and `PLATFORM_STAFF`) can never order food or use customer loyalty wallets; keeps Home Kitchen hosts cleanly inside `POS_STAFF` (`OWNER`/`STAFF` roles). | **Cons:** Requires updating `ActorSource` checks across `authorization.ts`, `scoped-repository.ts`, `auth-middleware.ts`, `orders`, `iam`, `support`, and test suites.
  - _Option B:_ **3-Actor Taxonomy Keeping `'GLOBAL_USER'` (`'ANONYMOUS' | 'GLOBAL_USER' | 'POS_STAFF'`)** — Eliminate `'SYSTEM'`, but keep `'GLOBAL_USER'` shared between Mobile + OTP customers and corporate-email platform staff via `globalRole`. — **Pros:** Smaller diff across existing files. | **Cons:** Preserves compound `actorSource === 'GLOBAL_USER' && !isPlatformAdmin()` branches across handlers instead of clean actor separation.
- **User Commentary & Trade-Off Evaluation:** Engineering Lead emphasized that:
  1. `POS_STAFF` and `PLATFORM_STAFF` logins are strictly for business activities, never for ordering food—anyone wishing to order food must use a separate personal `CUSTOMER` account.
  2. Customers authenticate exclusively via **Mobile + OTP** (`phoneNumber` plugin), while `PLATFORM_STAFF` register via corporate email and `POS_STAFF` via brand email, eliminating email uniqueness collisions on `"User"."email"`.
  3. Home Kitchen hosts and Drivers are modeled as domain roles/profiles (`OWNER`/`STAFF` tenant roles in `POS_STAFF` for Home Kitchen; `DriverProfile` / `DRIVER` role for drivers), and when a single mobile user manages both a personal `CUSTOMER` profile and a `HOME_KITCHEN` or `DRIVER` profile, they will switch active operational modes via an explicit token exchange rather than holding mixed rights in a single token.
- **Selected Implementation:** Define `export type ActorSource = 'ANONYMOUS' | 'CUSTOMER' | 'POS_STAFF' | 'PLATFORM_STAFF';`, initialize unauthenticated HTTP requests in `initDiScope` as `actorSource: 'ANONYMOUS'`, `actorId: ANONYMOUS_ACTOR_ID` (`00000000-0000-4000-8a00-000000000000`), `permissions: []`, and enforce strict actor-type guards on storefront, POS, support, and platform endpoints.

### Q3. Bootstrap DI Wiring (`bootScope`) & Per-Event Isolated Scopes

- **Considered Options (up to 5: Option A – Option E):**
  - _Option A (Selected):_ **Stateless `ANONYMOUS` `bootScope` + Per-Event Isolated Scopes** — Register domain event subscribers as singletons wired at boot using a stateless `bootScope` (`actorSource: 'ANONYMOUS'`, `actorId: BOOTSTRAP_ACTOR_ID`, `permissions: []`). Inside subscribers that invoke `ScopedRepository` (`BillingSettlementEventHandler`, `LoyaltySettlementEventHandler`), create and dispose a short-lived `rootContainer.createScope(...)` per event bound to the triggering event's `restaurantId` / `customerId`, `actorId`, and narrow domain permissions. — **Pros:** Zero shared mutable scope state across concurrent events, zero bypasses of `ScopedRepository`, negligible overhead (~0.02 ms in-memory map allocation), and full human `actorId` audit attribution. | **Cons:** Adds ~10 lines of scope lifecycle management (`createScope` / `try...finally dispose`) inside `BillingSettlementEventHandler` and `LoyaltySettlementEventHandler`.
  - _Option B:_ **Explicit Scope Parameters on Repository Methods** — Pass `restaurantId` / `userId` directly into `BillingRepository` and `LoyaltyRepository` methods without creating a DI scope per event. — **Pros:** Avoids creating a DI scope per event. | **Cons:** Creates an unchecked repository code path that bypasses `ScopedRepository` constructor-level `RequestContext` enforcement.
- **User Commentary & Trade-Off Evaluation:** Confirmed that `bootScope` should hold zero permissions at startup and only wire listeners, while runtime event handling resolves an isolated per-event scope so `ScopedRepository` enforces tenant/user boundaries on 100% of queries.
- **Selected Implementation:** Configure `bootScope` as `actorSource: 'ANONYMOUS'`, `actorId: BOOTSTRAP_ACTOR_ID` (`00000000-0000-4000-8b00-000000000000`), `permissions: []`, register `BillingSettlementEventHandler` and `LoyaltySettlementEventHandler` as singletons taking per-event scope factories, and dispose each per-event scope in `finally`.

## 3. Implementation Additions & Finalized Architecture Details

- **Generic Typed Per-Event Scope Factory (`src/core/application/scoped-factory.ts`):** Introduced `ScopedFactory<TService>` (`(request: RequestContext) => { readonly service: TService; dispose(): Promise<void> }`) and registered `DI_TOKENS.BILLING.SETTLEMENT_SERVICE_FACTORY` and `DI_TOKENS.LOYALTY.SETTLEMENT_SERVICE_FACTORY` in `src/container.ts` via a late-bound `createChildScope` hook, keeping `RequestContext` construction inside each domain event handler (`BillingSettlementEventHandler`, `LoyaltySettlementEventHandler`) and eliminating Service Locator lookups or circular container types.
- **Orders Command Handler Decomposition (`src/orders/application/`):** Split `src/orders/application/commands.ts` into `storefront-order-commands.ts`, `pos-order-commands.ts`, and `order-pricing-helpers.ts` (with `commands.ts` re-exporting public handlers) to satisfy Biome cognitive complexity rules while enforcing `CUSTOMER`-only storefront cart/checkout (`403` for `POS_STAFF`/`PLATFORM_STAFF`).
- **Merchant Loyalty Ledger User FK Attribution (`src/loyalty/application/commands.ts`):** Updated `redeemMerchantPointsForFeeOffset` to resolve a valid `"User"` foreign key when appending `MERCHANT` ledger entries while preserving `params.actorId` in audit columns (`createdBy`/`updatedBy`).
